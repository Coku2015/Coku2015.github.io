又要手工装 Kit 了？我写了 AgentBridge

v13 出来之前，给没加域的 Windows 机器装 Veeam Agent，从来不是件难事。

保护组里填上机器名和管理员账号，VBR 就能把 Agent 批量推下去。加域的没加域的都能推，没加域的机器顶多多填一个本地管理员的账号密码。

v13 主推的 VSA 出来之后，这招对没加域的 Windows 机器突然不管用了。

凭据填进去，点推送，等来的不是进度条，是报错。翻文档、逛论坛，最后都会指到同一个答案：先到每台机器上装一个叫 Deployment Kit 的小工具，装完它，VBR 才能连这台机器，Agent 才能继续推。

Kit 本身不复杂，装起来也不慢。问题是怎么装到几十台上百台机器上：官方给的路径基本是手工运行脚本，或者你自己有 SCCM、Intune 这类企业级分发工具。

没有 SCCM 的环境就剩一条路：远程桌面连上去，一台一台点。十几台咬咬牙也就忍了，几十台上百台，这个体验直接梦回解放前。

为什么突然不管用了？官方的说法是安全升级，VSA 对没加域机器的信任方式变了，以后改用证书。细节不用深究，记住结果就行：老的凭据推送这条路断了，而且不会回头。Windows 版的 v13 这条老路暂时还走得通，但 VSA 是 v13 主推的形态，新环境躲不开。

说到底，装 Kit 就是个重复劳动，最适合交给工具。我把它写了出来，就是 AgentBridge。今天发布第一个版本 v0.1.0。

项目地址：https://github.com/Coku2015/AgentBridge

AgentBridge 是什么？

一句话：一个专门负责 Agent 第一次安装的部署工具。把机器第一次接上 VBR 这件事做可靠，是它唯一的活。

具体动作就三步：把 Deployment Kit 装到目标机上，创建基于证书的保护组，交给 VBR 接管。之后 Agent 的推送、升级、备份、恢复，全部回到 VBR 的正常轨道。

形态上它是一个单独的可执行文件，Windows、Linux、macOS 都能跑。不需要安装，不需要起服务，终端里敲一下，浏览器自动打开控制台，全程网页操作。用完关掉，什么都不留下。

它是怎么把"推送安装"找回来的？

前面说的那个 Deployment Kit，其实就是 v13 发给没加域机器的新钥匙。

Kit 装好之后，它会和 VBR 之间建立一套基于证书的信任：VBR 通过一个证书认证的 Individual Computers 保护组认领这台机器，后面 Agent 的部署和管理，就都是 VBR 自己的事了。这条路是 v13 官方设计的正路，不是什么偏门技巧。

这套设计方向没问题，比老的凭据方式干净。卡住大家的从来不是原理，是"Kit 怎么批量装上去"这一步。

AgentBridge 干的就是这一步。Windows 上，它走 SMB 3 和计划任务 RPC：先预检 TCP/445 通不通、ADMIN$ 管理共享在不在、远程计划任务能不能用，然后把 Kit 上传到随机临时目录，远程执行官方安装脚本。装完还不算完，要确认 VeeamDeploySvc 服务已经跑起来、TCP/6160 能连通，才标记为成功，最后清理掉临时文件。

整个过程，你只需要在浏览器里填一次管理员账号密码。

顺带说一句：它不绕权限。目标机上该有的管理员权限一样不能少，它只是替你跑腿，不替你破例。

为什么是 AgentBridge？

找回"填个账号就能推"的手感。 这是它存在的理由。把没加域的 Windows 机器一台台加进来，填上管理员账号，AgentBridge 远程把 Kit 装好、验证好，全程你坐在自己电脑前操作。v12 时代顺手就能做的事，到了 v13 也应该能顺手做。

密码只是用一下，不留底。 老方式为了推送，VBR 里得存一批本地管理员凭据，年年被安全审计问一遍。AgentBridge 的账号密码只在安装那一刻在内存里用一下，任务结束就清掉，不落盘、不进日志。留在 VBR 里的只有一个证书认证的保护组。审计再来问，你底气也足。

不用为这件事去凑一套 SCCM。 Kit 和 Linux Agent 安装包都直接从你自己的 VBR 导出，版本永远和服务器匹配。不需要额外的分发服务器，不需要企业级工具，一个可执行文件把事办完。

推不进去的机器，发条命令过去。 有些环境网络管得严：管理共享不开，Remote UAC 拦着，远程路径进不去。这时候 AgentBridge 在本地起一个临时下载服务，生成一条 PowerShell 命令。发给机器前的同事，复制、粘贴、回车，脚本自己提权、下载、校验、安装。下载令牌单次有效，30 分钟过期。你不用自己远程桌面过去。

Linux 顺手一起办了。 同一个界面里，Linux 走 SSH：自动认发行版和架构，从 VBR 挑出匹配的安装包，root 密码、免密 sudo、sudo 密码这些姿势都支持。最后 Windows 和 Linux 进的是同一个证书保护组，VBR 一视同仁。

官方不待见的系统，强行装。 CentOS 这类系统，Veeam 多年前就停止正式支持了，但现实里这些机器还成片跑着。AgentBridge 遇到官方不认的发行版，会按包格式、架构和系统版本推断出最匹配的安装包，让你强行装上去。装之前它会明确提示这是非官方路径，需要你亲手确认；推荐的安装包也带着"推断兼容"的标记，和官方支持的路径分开，不会搞混。

“装好了"和"认到了”，分开显示。 “本机装好了"和"VBR 认到了"是两回事，中间隔着保护组和 Rescan。AgentBridge 把这两层状态分开摆出来，卡在哪一步一眼看清。不然装的时候一片绿色，回头才发现 VBR 根本没认领，找问题都没处下手。这个细节不起眼，真出事的时候救命。

完整走一遍：从裸机到 VBR 接管

以最典型的场景为例：v13 VSA 环境，一批没加域的 Windows 机器。

第一步，下载运行。 Releases 页面下载对应系统的包，解开就一个文件：

agentbridge

起来之后浏览器自动打开控制台，剩下的都在网页里点。

第二步，连接 VBR。 需要 VBR v13.1。填地址和账号，点连接。然后生成 Deployment Kit，组件从你的 VBR 现场导出。

第三步，添加主机。 把机器一台台加进去，可以选择Windows或者Linux平台。每台填一次性管理员凭据，AgentBridge 先跑预检：445、ADMIN$、计划任务 RPC，一项项过。Remote UAC 拦住了会明确告诉你卡在哪，不会甩一句模糊的报错。

第四步，部署。 能推的机器直接远程安装；推不进去的切手工模式，把那条 PowerShell 命令发给机器前的同事。装完自动验证 VeeamDeploySvc 服务和 6160 端口，不通过不算成功。

第五步，创建保护组。 选就绪的主机，创建证书认证的保护组，自动触发 Rescan。

第六步，等 VBR 认领。 Rescan 完成后，VBR 按保护组的设置把这批机器的 Agent 部署下去。从这一刻起，升级、备份、恢复全部回到 VBR 的正常轨道，AgentBridge 功成身退，下次有新机器再来找它。
